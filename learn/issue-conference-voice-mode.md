# Issue: 会议培训语音模式体验完善

## Title

fix: improve conference training voice mode

## 背景

会议培训当前已经支持文字模式，但用户在选择“语音”模式进入会议后，体验仍不符合真实语音训练预期：

- 从会议训练卡片选择“语音”后，会议页仍可能以文字模式打开。
- 进入语音模式后，用户说话没有反应，仍需要手动点击“开始语音录制”。
- 语音转写依赖手动停止录音，不适合会议演讲和 Q&A 的连续口语交互。
- HCP 语音播报时，前端仍可能监听麦克风，导致系统播报被误识别为用户发言。
- 多个 HCP 文本事件靠近触发时，TTS 可能并发播放，出现两个 HCP 同时说话。

会议培训的语音模式需要更接近真实会议：用户进入语音模式后可以直接讲话，系统自动判断一句话结束并转写，HCP 依次播报，不互相重叠。

## 目标

完善会议培训语音模式，使用户从训练入口选择语音后，可以在会议页获得连续、自然、无重叠的语音交互体验。

## 用户故事

作为 MR 学员，
我希望选择会议“语音”模式后可以直接开始演讲和回答 HCP 问题，
以便像真实会议一样自然练习，而不是每句话都手动点击录音开始和结束。

作为 MR 学员，
我希望多个 HCP 的语音按顺序播放，
以便我能清楚听到每位 HCP 的问题，而不是多个人同时出声。

## 需求范围

### 1. 会议训练入口模式传递

- 会议训练卡片需要支持文字与语音模式选择。
- 用户选择语音模式后，创建会议 session 并跳转到会议页时需要携带语音模式参数。
- 会议页应根据入口参数初始化为语音输入模式。
- 不应把 F2F 的数字人实时模式误用到会议页；会议语音模式使用会议页现有 STT + TTS 能力。

### 2. 语音模式自动监听

- 会议页进入语音模式后，应自动启动麦克风监听。
- 用户不需要额外点击“开始语音录制”才能讲话。
- 切换回文字模式、会议完成或页面不应继续监听时，需要停止录音。
- 保留麦克风按钮作为手动控制入口，用于用户主动暂停或恢复。

### 3. 自动停句与转写发送

- 流式 STT 应支持前端静音检测。
- 检测到用户开始说话后，如果持续静音达到阈值，应自动结束当前发言轮次。
- 前端自动发送 stop 信号给后端 STT stream，使后端返回最终转写文本。
- 转写文本应进入会议已有发言逻辑：
  - 普通演讲阶段发送 `present`。
  - 有待回答 HCP 问题时发送 `respond`。
- 一轮转写完成后，如果仍处于语音模式，应自动恢复监听下一轮发言。

### 4. HCP 播报期间暂停监听

- HCP TTS 播报期间，前端应暂停用户麦克风监听。
- 播报结束后，如果仍处于语音模式，应自动恢复监听。
- 这样可以避免把系统播报声重新转写成 MR 发言。

### 5. 多 HCP 语音顺序播放

- 会议页收到多个 `speaker_text` 事件时，HCP TTS 不能并发播放。
- HCP 语音应进入播放队列，上一段播完后再播放下一段。
- 普通聊天场景的 TTS 行为可以保持“新语音打断旧语音”；队列播放应作为会议页可选能力启用。

## 验收标准

- [ ] 在会议训练卡片选择“语音”后，进入会议页默认就是语音输入模式。
- [ ] 会议页 URL / state 能明确表达当前输入模式，例如 `inputMode=audio`。
- [ ] 进入语音模式后，不点击麦克风按钮也会自动开始监听。
- [ ] 用户说完一句话后，系统能自动停止当前轮录音并转写。
- [ ] 转写成功后，MR 发言会出现在会议对话 / 转写流程中。
- [ ] 一轮发言结束后，系统会继续自动监听下一轮。
- [ ] HCP 播报时不会继续监听用户麦克风。
- [ ] HCP 播报结束后会恢复自动监听。
- [ ] 两个或多个 HCP 连续发言时，TTS 按顺序播放，不会同时出声。
- [ ] 切回文字模式后，自动监听停止。
- [ ] 会议完成后，自动监听停止。
- [ ] 语音服务不可用或麦克风授权失败时，页面有错误提示，且不会卡在录音状态。

## 技术建议

### Frontend

- `frontend/src/pages/user/training.tsx`
  - 会议训练启动时不要丢弃用户选择的 mode。
  - 将会议语音选择映射为会议页输入模式，例如 `inputMode=audio`。
  - 会议卡片只暴露会议实际支持的模式：文字、语音。

- `frontend/src/pages/user/conference-session.tsx`
  - 从 URL / search params 初始化 `inputMode`。
  - 在 `inputMode === "audio"` 且 session 可用时自动调用 `startRecording()`。
  - 在 TTS 播报、切回文字、会议完成时调用 `stopRecording()`。
  - 使用队列模式 TTS 播放 HCP 发言。

- `frontend/src/hooks/use-speech.ts`
  - 为 `useStreamingSpeechInput()` 增加可选静音检测配置：
    - `autoStopOnSilence`
    - `silenceMs`
    - `voiceThreshold`
    - `minSpeechMs`
    - `noSpeechTimeoutMs`
  - 静音检测触发后自动发送 `{ type: "stop" }` 给 `/api/v1/speech/stream`。
  - 为 `useTextToSpeech()` 增加可选 `queue` 模式，使会议页可以顺序播放多段 HCP 语音。

### Backend

- 复用现有 `/api/v1/speech/stream` WebSocket STT 能力。
- 当前后端 STT stream 已支持：
  - 接收 PCM audio bytes。
  - 接收 `{ "type": "stop" }` 后停止当前连续识别。
  - 返回 `done` 事件和最终文本。
- 本 Issue 不要求引入新的后端 endpoint，除非后续需要 server-side VAD。

## 测试建议

### Frontend Unit

- 训练页：选择会议语音模式后跳转 URL 携带 `inputMode=audio`。
- 会议页：无参数默认文字模式；`inputMode=audio` 时初始化为语音模式。
- 会议页：进入语音模式后自动调用 `startRecording()`。
- 会议页：文字模式不自动调用 `startRecording()`。
- 会议页：完成 session 不自动监听。
- 会议页：切换到 audio 后开始监听，切回 text 后停止监听。
- Speech hook：静音检测开启时能自动触发 stop。
- TTS hook：queue 模式下第二段音频不会在第一段结束前播放。

### E2E / Manual Smoke Test

- 从会议训练卡片选择“语音”，进入会议页后直接说话。
- 确认无需点击麦克风按钮，发言能被转写并发送。
- 等 HCP 播报问题时保持安静，确认系统不会把 HCP 声音识别成 MR 发言。
- 配置多个 HCP 连续提问，确认语音按顺序播放。
- 切换到文字模式，确认麦克风监听停止。
- 结束会议，确认不会继续录音。

## 非目标

- 不在本 Issue 中实现真正的全双工低延迟实时对话模型。
- 不在本 Issue 中替换 F2F Voice Live / 数字人能力。
- 不在本 Issue 中实现服务端 VAD；当前优先使用前端静音检测。
- 不在本 Issue 中改造会议主持人和 HCP 的 Prompt 编排能力，该能力由会议 Prompt 配置 Issue 跟进。

## 相关说明

会议语音模式当前定义为：会议页内的 STT 输入 + HCP TTS 播报。它不同于 F2F 的 Voice Live / 数字人实时模式。后续如果会议也需要数字人或全双工实时语音，应单独设计会议 Voice Live 架构，避免和当前会议 STT/TTS 模式混用。
