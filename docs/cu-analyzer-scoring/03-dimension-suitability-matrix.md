# 03 — 评分维度适用性矩阵

> 逐维度分析每个评分维度应使用 CU、LLM 还是代码逻辑，以及推荐的混合方案。

---

## 1. 当前评分维度一览

### 内容评分维度 (Content Scoring)

| 维度 | 权重 | 评估内容 |
|------|------|---------|
| key_message | 30% | MR 是否传递了规定的关键信息 |
| objection_handling | 25% | MR 如何应对 HCP 的异议/抵触 |
| communication | 20% | 沟通技巧、主动倾听、专业用语 |
| product_knowledge | 15% | 产品信息的准确性和深度 |
| scientific_info | 10% | 临床数据引用、循证论据 |

### 语音评分维度 (Voice Scoring)

| 维度 | 权重 | 评估内容 |
|------|------|---------|
| fluency | 25% | 语言流畅度、停顿频率 |
| tone | 25% | 语调专业度、情感适当性 |
| pace | 25% | 语速节奏、均匀性 |
| pronunciation | 25% | 发音清晰度、医学术语准确性 |

---

## 2. 逐维度详细分析

### 2.1 key_message (关键信息传递) — 权重 30%

| 评估要素 | 需要的信息 | CU 能获得？ | LLM 能获得？ |
|----------|-----------|------------|-------------|
| MR 说了哪些 key messages | Key messages 列表 | ❌ | ✅ |
| 每条 key message 的覆盖程度 | 原文 + 对比标准 | ❌ | ✅ |
| 传达的自然度/流畅度 | 对话上下文 | ⚠️ 部分 | ✅ |
| 是 MR 说的还是 HCP 提的 | role 语义理解 | ❌ | ✅ |
| 覆盖了几条/总共几条 | 统计数据 | ❌ | ✅ |

**结论: ❌ CU 不适合，✅ LLM 适合**

**推荐方案:**
```
1. 代码逻辑: 计算 delivery_ratio (已有 key_messages_status)
2. LLM 评分: 评估传递质量、自然度、深度
3. 硬约束: delivery_ratio < 25% → 维度分数 cap 30
```

---

### 2.2 objection_handling (异议处理) — 权重 25%

| 评估要素 | 需要的信息 | CU 能获得？ | LLM 能获得？ |
|----------|-----------|------------|-------------|
| HCP 提出了哪些异议 | HCP objections 设定 | ❌ | ✅ |
| MR 是否识别了异议 | 对话语义理解 | ⚠️ | ✅ |
| MR 用了什么证据反驳 | 产品/临床数据参照 | ❌ | ✅ |
| MR 是否先认可再反驳 | 对话策略分析 | ⚠️ | ✅ |
| 反驳的准确性 | 正确的反驳论据 | ❌ | ✅ |

**结论: ❌ CU 不适合，✅ LLM 适合**

**推荐方案:**
```
LLM 评分: 结合 HCP profile.objections 列表评估 MR 的应对策略
前置检查: 如果对话中 HCP 没有提出异议 → 维度标记 N/A 或给基础分
```

---

### 2.3 communication (沟通技巧) — 权重 20%

| 评估要素 | 需要的信息 | CU 能获得？ | LLM 能获得？ |
|----------|-----------|------------|-------------|
| 主动倾听表现 | 对话模式分析 | ⚠️ 有限 | ✅ |
| 语言专业度 | 文本分析 | ⚠️ 有限 | ✅ |
| 适应 HCP 沟通风格 | HCP 风格设定 | ❌ | ✅ |
| 反思性倾听技巧 | 对话策略 | ⚠️ 有限 | ✅ |
| 只评估 MR (非 HCP) | role 区分 | ❌ | ✅ |

**结论: ❌ CU 不适合（无法区分角色、无法评估"适应性"），✅ LLM 适合**

**注意:** 这个维度虽然不强依赖产品知识，但需要:
1. 区分 MR 和 HCP 的发言
2. 知道 HCP 的沟通风格设定（0-100 直接↔间接）
3. 评估 MR 是否"适应"了该风格

---

### 2.4 product_knowledge (产品知识) — 权重 15%

| 评估要素 | 需要的信息 | CU 能获得？ | LLM 能获得？ |
|----------|-----------|------------|-------------|
| 产品信息是否准确 | 正确的产品信息 | ❌ | ✅ |
| 剂量/给药知识 | 产品说明书 | ❌ | ✅ |
| 竞品对比能力 | 竞品数据 | ❌ | ✅ |
| 知识深度 | 细节程度 | ⚠️ | ✅ |
| 是 MR 展示的还是 HCP 说的 | role 语义 | ❌ | ✅ |

**结论: ❌ CU 完全不适合，✅ LLM 适合**

这是最需要外部知识参照的维度 — 评估"MR 说的对不对"必须有"什么是对的"作为参照。

### 2.5 scientific_info (科学信息) — 权重 10%

|----------|-----------|------------|-------------|
| 是否引用了具体研究 | 研究名称参照 | ❌ | ✅ |
| 研究数据是否准确 | 正确的临床数据 | ❌ | ✅ |
| 患者人群讨论 | 适应症知识 | ❌ | ✅ |
| 终点数据引用 | 试验终点数据 | ❌ | ✅ |

**结论: ❌ CU 完全不适合，✅ LLM 适合**

### 2.6 fluency (流畅度) — 语音维度

| 评估要素 | 需要的信息 | CU 能获得？ | LLM 能获得？ |
|----------|-----------|------------|-------------|
| 停顿频率 | 音频信号 | ✅ | ❌ 无法分析音频 |
| 语句连贯性 | 语音流分析 | ✅ | ❌ |
| 填充词使用 (呃、嗯) | 音频特征 | ✅ | ⚠️ 只能从 transcript |
| 断句自然度 | 音频时序 | ✅ | ❌ |

**结论: ✅ CU 非常适合，❌ LLM 无法直接评估**

### 2.7 tone (语调) — 语音维度

| 评估要素 | 需要的信息 | CU 能获得？ | LLM 能获得？ |
|----------|-----------|------------|-------------|
| 热情度/积极性 | 音频情感 | ✅ | ❌ |
| 专业度 | 声音特征 | ✅ | ❌ |
| 情感适当性 | 语调变化 | ✅ | ❌ |
| 单调 vs 有变化 | 音频信号 | ✅ | ❌ |

**结论: ✅ CU 非常适合，❌ LLM 无法直接评估**

## 3. 综合适用性矩阵

| 维度 | 模态 | CU 适合度 | LLM 适合度 | 推荐引擎 | 原因 |
|------|------|-----------|-----------|----------|------|
| key_message | 文本 | ❌ 0/5 | ✅ 5/5 | **LLM** | 需要 key messages 列表 + delivery status |
| objection_handling | 文本 | ❌ 1/5 | ✅ 5/5 | **LLM** | 需要 HCP objections + 策略评估 |
| communication | 文本 | ⚠️ 2/5 | ✅ 5/5 | **LLM** | 需要角色区分 + HCP style 参照 |
| product_knowledge | 文本 | ❌ 0/5 | ✅ 5/5 | **LLM** | 需要正确产品知识参照 |
| scientific_info | 文本 | ❌ 0/5 | ✅ 5/5 | **LLM** | 需要正确临床数据参照 |
| fluency | 音频 | ✅ 5/5 | ❌ 0/5 | **CU** | 纯音频信号分析 |
| tone | 音频 | ✅ 5/5 | ❌ 0/5 | **CU** | 纯音频信号分析 |
| pace | 音频 | ✅ 5/5 | ❌ 0/5 | **CU** | 纯音频信号分析 |
| pronunciation | 音频 | ✅ 5/5 | ❌ 0/5 | **CU** | 纯音频信号分析 |

---

## 4. 决策规则

### 规则 1: 按模态分流

```
音频信号相关维度 → CU (prebuilt-audioAnalyzer)
文本内容相关维度 → LLM (Azure OpenAI)
```

### 规则 2: 按上下文需求分流

```
需要外部上下文 (产品/key messages/HCP profile) → LLM
只需分析输入内容本身的属性 → CU
```

### 规则 3: 按"正确答案"需求分流

```
有"正确答案"需要对比 (key messages, 产品知识) → LLM
无"正确答案"概念 (说话是否流畅) → CU
```

## 5. 特殊情况讨论

### 5.1 如果未来 CU Pro 模式支持文本+参考数据？

即使 Pro 模式将来支持传入参考文件，仍然存在:
- field description 1024 字符限制
- 无 system prompt 等价物
- Pro 模式 token 成本与 LLM 接近，无成本优势
- LLM 在语义理解上仍然更强

**结论:** 即使 Pro 模式可用，LLM 对内容评分仍是更优选择。

### 5.2 如果要评估"MR 的语音内容+语音质量"组合？

可以让 CU 的语音 analyzer 同时输出:
1. re-transcription (transcript) — 用于内容评分的补充输入
2. 语音质量维度评分

但**内容评分仍由 LLM 基于 transcript 执行**，不应让 CU 评估内容正确性。

### 5.3 Conference 模式 (多人对话) 的特殊考量

Conference 模式有多个 speaker，CU 的音频分析需要:
- 说话人分离 (diarization)
- 只评估 MR 的语音（排除其他参与者）

CU 的 `prebuilt-audioAnalyzer` 支持说话人分离，适合此场景。
